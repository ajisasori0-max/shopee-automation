## Design Decisions

- Ingestion is a first-class bounded context at `commerceos/ingestion/`.
- The dependency direction is: **Marketplace Connector → Ingestion → Canonical Commerce**.
- The Sync Engine owns the orchestration: it calls the connector, persists raw payloads, maps to canonical entities, and records provenance.
- Raw payloads are deduplicated by `(marketplace_code, store_id, entity_type, external_entity_id, payload_hash)`.
- Sync checkpoints are explicit and deterministic. The engine resumes from the checkpoint, not from inferred SyncRun history.
- Failed syncs do not update checkpoints, so the next run resumes from the last successful position.
- Connector errors are classified as `auth_error`, `rate_limit`, `transient_error`, `permanent_error`, or `connector_error`, with retryability flags.
- The SQLite schema is designed for future PostgreSQL migration (no SQLite-specific features, UTC timestamps, UUID-compatible strings).

## Trade-offs

| Decision | Pros | Cons |
|----------|------|------|
| Ingestion tables in canonical DB | Single backup, simple ops, fast iteration | Raw data grows alongside canonical data; future split possible |
| Payload hash deduplication | True idempotency, no duplicate raw rows | Hash computation overhead is negligible |
| Explicit checkpoints | Resume is deterministic and simple | Requires connector to return meaningful cursor |
| UoW commits per sub-operation | Easier to reason about partial failure | More transactions than a single batch sync; acceptable for Epic 1 |

## Known Limitations / Technical Debt

- The Sync Engine currently accesses the canonical model session via `getattr(uow, "session", None)`. This is temporary; in the next refactor, canonical persistence will go through its own repository interface.
- Raw payload store is in the same database. Future work: move to S3/PostgreSQL partitions/event store.
- No retry/backoff logic in Sync Engine yet (to be added in Epic 2 or later in E1.3).
- Health check integration with SyncRun is not yet implemented.
- The Sync Engine assumes one entity type per sync run. Future support for batch multi-entity sync runs is possible but not in scope.
- Connector fetch methods are routed by entity type string matching (`orders`, `products`, etc.). A more robust registry could be added later.
